## 1. 최종 아키텍처 요약

* **완성된 아키텍처 핵심**
  * LangGraph 기반 Multi-Agent(공고서 분석 `NoticeScanAgent` + 조달 상담 `PpsAssistAgent`) 워크플로우를 구축했습니다.
  * RAG 도구를 별도 프로세스로 분리한 MCP(Model Context Protocol) SSE 도구 서버(`llm-mcp-doc-rag`) 연동 파이프라인을 완성했습니다.
  * 법령 문서는 조/항/호/별표 계층을 인식하는 LawChunker(Parent-Child 청킹)와 파일별 독립 FAISS 인덱스로 구축하고, LLMRerank로 근거 품질을 보정하는 Advanced RAG 구조를 적용했습니다.

* **최종 산출물 형태**
  * 공공기관 조달·계약 담당 주무관을 위한 웹 기반 **'공공조달 어시스턴트'** 서비스를 하나의 React 애플리케이션으로 통합 제공합니다.
  * **공고서 파싱 에이전트 화면:** 공고서(PDF/HTML) 업로드 시 나라장터 입력 항목에 매핑된 구조화 데이터(JSON)를 생성하여 상세정보, 품목, 공고입력 데이터(JSON), 원문 탭으로 제공하고 원클릭 복사 기능을 지원합니다.
  * **조달 법령·지침 기반 대화형 Q&A 챗봇:** SSE 실시간 스트리밍을 지원하는 챗봇 환경을 제공합니다.
  * **배포 환경:** React UI, FastAPI 서버, MCP 서버, PostgreSQL을 각각 Dockerfile 및 docker-compose로 컨테이너화하여 배포 환경을 일원화했습니다.

* **Agent 구조 및 워크플로우**
* **요청 흐름:** React UI(8501 포트)에서 에이전트 선택 ➡️ FastAPI `llm-server`(9001 포트)의 `/api/v1/convrstn/question`(또는 `/api/v1/notice-scan`)으로 요청 전송 ➡️ 해당 LangGraph 에이전트가 실행되어 MCP 도구 서버를 SSE 방식으로 호출 ➡️ 노드별 진행 상태(progress 이벤트)와 최종 답변을 실시간 스트리밍으로 반환하고, 최종 결과를 PostgreSQL에 저장합니다.
* **NoticeScanAgent (공고서 분석):** `convert_to_markdown` 노드(MCP 도구를 활용해 PDF는 pymupdf4llm, HTML은 MarkItDown으로 변환) ➡️ `check_parsing_status`(조건부 엣지 라우터) ➡️ 정상 시 `extract_metadata` 노드로 진입(Pydantic의 `with_structured_output`을 활용해 general, execution, items 등 5개 구조를 가진 `ProcurementData` 추출. 이때 규정 저촉 의심 조항인 `regulatory_review_notice`가 존재하면 `is_violating` 플래그 세팅) ➡️ 변환 실패 시 `error_handler`로 분기하여 원인 메시지와 함께 프로세스를 종료합니다. 이때 `get_stream_writer`를 통해 노드별 진행 이벤트를 SSE로 중계합니다.
* **PpsAssistAgent (조달 상담 Q&A):** `Start Conversation`(대화 세션 생성 및 최근 대화 6건 기반 맥락 요약) ➡️ `Query Rewrite`(대명사 치환·상대 날짜 변환 등으로 맥락을 강화한 질의문 생성) ➡️ `Document Search`(첨부 문서가 존재할 경우 MCP `qna_doc` 호출) ➡️ 외부 문서 검색 허용 여부에 따라 분기합니다. `Law Base Search`(LLM이 일반용역/기술용역/시설공사/물품/비축 5개 전문 분야 중 agent_mode를 자동 분류한 후 MCP `qna_law_base` 호출) 또는 `Web Search`(MCP `qna_web_search`) 과정을 거칩니다. 최종적으로 수집된 근거를 페르소나 및 최종 답변 프롬프트와 결합하여 토큰 단위로 스트리밍합니다.
* **외부 시스템 연동:** MCP SSE 서버는 `qna_doc`, `qna_law_base`, `qna_web_search`, `convert_to_markdown` 4개 도구를 구동하며, 내부적으로는 '질문 분해 ➡️ 엔진 준비 ➡️ `asyncio.gather`를 통한 병렬 RAG 실행' 구조의 LangGraph로 구성되어 있습니다. LLM 및 임베딩 모델은 환경변수를 통해 Azure OpenAI(GPT / `text-embedding-3-small`)와 로컬 인프라(Ollama / `ko-sroberta-nli`) 간 자유로운 전환이 가능합니다. 데이터 영속화를 위해 PostgreSQL(`convrstn`, `convrstn_details`)을 연동하였으며, 전문 분야별로 사전 로딩된 LlamaIndex 쿼리 엔진 및 FAISS 인덱스를 활용합니다.

### 2-1. 공고문 입력 양식 추출 정확도 평가 상세
* 필드 단위 대조 결과 (Precision / Recall 평가)
  - **평가 대상 필드:** 총 25개 (general 12 + execution 6 + items 7)
  - **정답 값 존재 필드:** 23개 (unitPrice, amount는 정답이 null)
    | 구분 | 판정 기준 | 필드 수 | 해당 필드 |
    |---|---|---|---|
    | 정확 추출 (TP) | 표본과 값 완전 일치 | 18 | noticeNo, contractMethod, awardMethod, quantity 등 |
    | 오추출 (FP=FN) | 값이 존재하나 표본과 불일치 | 5 | noticeName, agency, bidStartDate(시각), openPlace, standard |
    | 정상 미추출 (TN) | 표본 null → 생성도 null | 2 | unitPrice, amount (환각 없이 null 유지) |

* 평가 지표 산출
  | 지표 | 산식 | 결과 |
  |---|---|---|
  | Precision | TP / (TP + FP) = 18 / 23 | **78.3%** |
  | Recall | TP / (TP + FN) = 18 / 23 | **78.3%** |
  | F1-Score | 2 × (P × R) / (P + R) | **78.3%** |

  > **참고:** 오추출 5건 중 4건(noticeName, agency, openPlace, standard)은 표본 값을 포함하되
  > 부가 정보를 덧붙인 과잉 추출(over-extraction) 유형으로, 부분 일치를 인정하는
  > 완화(lenient) 기준 적용 시 22/23 = **95.7%**. 순수 오류는 bidStartDate 시각 오추출 1건.


## 3. 창출된 핵심 가치

### 3-1. 비즈니스 가치

* 공고문 정독~전자시스템 입력 데이터 마련까지의 반복 행정 업무를 자동화하여, 공고당 1~2시간 걸리던 검토·재가공 작업을 3분 내외로 단축

* 규정 저촉 의심 조항을 `regulatory_review_notice`로 사전 스크리닝하여 감사 지적·발주 취소 등 행정·법적 리스크를 입력 단계에서 차단

* 순환 보직으로 조달 업무가 처음인 초임 주무관도 법령 근거(조항)가 첨부된 Q&A 답변을 통해 숙련 선임급 수준의 속도·신뢰도로 업무 수행 가능

### 3-2. 기술적 가치

* 단순 Q&A가 아닌, 비정형 공고서를 나라장터 입력 항목에 매핑된 구조화 JSON으로 변환해 실제 업무 시스템 입력까지 이어지는 Actionable Agent 구조 구현

* RAG 도구를 MCP 서버로 분리하여 에이전트-도구 간 결합도를 낮추고, 도구 재사용성(공고 분석·상담 에이전트가 동일 도구 서버 공유)과 독립 배포·확장성 확보

* 한국 법령 특유의 조/항/호/별표 계층을 인식하는 도메인 특화 청킹(LawChunker, tiktoken 토큰 기준 Parent-Child 분할) + 파일별 독립 FAISS 인덱스로 특정 문서의 Top-K 독점을 막는 검색 편향 해소 경험 확보

## 4. 운영 및 보안 고려 사항

* 인증 방식: 현재는 대화 세션(conversation_id, UUID) 단위로 사용자·대화 이력을 구분 관리 (정식 사용자 인증은 향후 과제)

* 권한 통제: CORS 허용 오리진을 Streamlit UI(localhost:8501)로 한정, MCP 도구 서버는 127.0.0.1 바인딩으로 내부 호출 전용, 법령 벡터 인덱스(FAISS)는 Read-only 참조로 한정

* 업로드 파일 처리: 업로드 파일명에 `os.path.basename` 정제 + UUID 접두사를 적용해 경로 조작(Path Traversal) 및 파일명 충돌 차단

* 환각(Hallucination) 대응: `with_structured_output()` + `Literal` 타입으로 계약방법·낙찰방법 등 코드성 필드의 출력값을 사전 정의 범위로 강제하고, 원문에 없는 항목은 추론 없이 `null` + extraction_note(사유)로 명시

* 장애 대응: 문서 변환/추출 실패 시 `error_handler` 노드가 원인 메시지를 담아 조기 종료, MCP 도구 호출 실패는 try/except로 감지해 `status="failed"` 전파, 스트리밍 중 예외 발생 시에도 실패 사유가 담긴 result 이벤트를 반드시 전달해 클라이언트 무한 대기 방지, 클라이언트 연결 끊김 시 나머지 답변을 일괄 생성해 DB 저장 보장
